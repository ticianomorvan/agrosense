# Supabase setup

The initial migration creates `farms`, `plots`, `crop_cycles`, `events`, and
`plot_alerts` from [the agreed domain model](domain-model.md). It includes foreign
keys, CHECK constraints, indexes, update timestamps, owner-scoped SELECT policies,
and revoked anonymous access and direct authenticated writes.

Migration `20260912070000_initial_schema.sql` was applied on 2026-09-12 to project
`obirprtxsujpgnxcjwwe` (AgroSense, PostgreSQL 17.6) through the Supabase dashboard.
The same version is recorded in `supabase_migrations.schema_migrations`; its
metadata table has RLS enabled. No application records or Auth users were seeded.

## Local environment

Copy `apps/api/.env.example` to `apps/api/.env` and fill the four settings. Wrangler
loads this file beside `wrangler.jsonc`. The supplied project settings are already
saved in this workspace's ignored `.env`. `.dev.vars`, if present, takes precedence.
Never prefix the secret key with `VITE_`, commit it, or return it to a browser.

`pnpm dev` uses the configured hosted Supabase project. The public `/api/health`
route still works without credentials. `GET /api/session` requires a Supabase Auth
access token in `Authorization: Bearer <token>` and returns `{ "userId": "<uuid>" }`.
Missing, expired, or invalid tokens return 401; unavailable configuration/JWKS
returns 503. Session responses use `Cache-Control: no-store`.

The reusable `requireAuth` middleware verifies ES256/RS256 signatures against the
configured issuer's JWKS, audience, expiry, UUID subject and `authenticated` role.
The existing hosted project uses ES256. Legacy HS256 tokens are intentionally
unsupported. Verification is local to the token's lifetime: immediate session
revocation requires an Auth-server lookup when a future feature needs it.

Authenticated handlers receive `c.get('userId')` and a typed,
request-scoped `c.get('supabase')` client. It sends the publishable key and the
verified user JWT to the Data API, preserving RLS. The secret key is reserved for
explicit administrative/seed operations; there is no privileged request client or
generic SQL endpoint.

## Migrations and types

Authenticate the CLI once and link this checkout before future remote operations:

```sh
pnpm exec supabase login
pnpm exec supabase link --project-ref obirprtxsujpgnxcjwwe
pnpm exec supabase migration list --linked
pnpm exec supabase migration new descriptive_name
pnpm exec supabase db push --linked --dry-run
pnpm db:push
pnpm db:types
```

The API keys in `.env` are Data API credentials, not CLI management credentials or
a database password. Supply CLI/database credentials through the CLI's prompt or
its documented environment variables. Do not put a password in a committed script.
`db:types` updates `apps/api/src/lib/database.types.ts` only after successful
Supabase type generation. The initial types were generated by introspecting the
migration in PGlite, including defaults, nullable columns, and foreign keys.

For a disposable local Supabase stack, start Docker and run `pnpm db:start`.
`pnpm db:reset` resets **only the local database**, reapplies migrations, and erases
local records. `pnpm db:stop` stops that stack. To use it in the API, replace the
`.env` settings with local values and configure asymmetric Auth signing keys per
[Supabase local configuration](https://supabase.com/docs/guides/local-development/cli/config).
The local config uses PostgreSQL 17 and SPA redirect URLs. Docker was unavailable
during initial setup, so the full local stack has not been exercised.

`pnpm db:test` executes the migration in isolated PGlite PostgreSQL with mock
Supabase roles/Auth. It checks both owners across all five tables, anonymous
access, direct writes, cross-farm FKs, crop constraints, timestamps, and deletion
behavior. It runs as part of `pnpm check` without Docker or cloud credentials.
These tests validate SQL/RLS, not the full GoTrue/PostgREST stack.

## Remaining product slices

The dashboard read route, snapshot RPC, and crop-cycle mutation RPC are
implemented. A validated demo seed/importer, sign-in UI, and forecast
publication remain separate features. The [weather adapter](domain-model.md#implemented-weather-adapter)
returns forecasts and detected events without writing to Supabase. JSONB
constraints currently check structural/version markers; trusted import/publication code must validate complete payloads and geometry topology.
Mutation RPCs verify ownership and implement the farm lock/version protocol from
the domain model. Updating `updated_at` does not increment `data_version`.

For a Cloudflare deployment, provision the four Worker settings with Wrangler
secrets or the Cloudflare dashboard; `.env` is for local development. Deployments
are separate from database migrations and were not performed during this setup.

References: [Data API keys](https://supabase.com/docs/guides/api/api-keys),
[database migrations](https://supabase.com/docs/guides/deployment/database-migrations),
[Wrangler local variables](https://developers.cloudflare.com/workers/local-development/environment-variables/).
